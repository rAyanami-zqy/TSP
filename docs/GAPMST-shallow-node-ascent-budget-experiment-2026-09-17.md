# GAPMST 浅层节点势上升预算实验

## 结论

当前分支势上升已经有安全早停：每轮取得的最强下界一旦满足正式
`shouldPrune` 谓词，就立即省掉剩余迭代。它没有“连续若干轮不改善就退出”
的预测式早停；Polyak 连续 4 轮不改善只把 `step_scale` 折半。可选 probe
能够按早期 gap 覆盖率拒绝一次更新，但默认关闭。

`--hk-update-max-depth 8` 只适合当观测窗口，不能当搜索策略。同一套
`subtree-adaptive` + Polyak 配置下，把更新限制在 depth<=8 会把
`n≈96–120` 的搜索树放大一到三个数量级，并制造虚假的 32/48/64 预算相变。
允许全部深度更新后，`rd100` 的 32 轮从 >120s 变成 1.23s，`gr120` 的 32 轮
从 >120s 变成 15.5s。

在不限制更新深度时，7 个实例没有单一最优上限。把同一口径扩到 33 个
`n<=100` 经典实例后，结论仍然分裂，但总量偏向 64：

- 有实质搜索的 18 个实例里，created 上 32 与 64 各赢 9 个；
- 32 赢在中小树（`gr96`、`st70`、`rat99`、`kroA100` 等）；
- 64 赢在困难尾部（`gr120`、`rd100`、`kroE100`、`kroD100`、`kroC100`）；
- 18 个实质实例合计 created 降到 32 轮的 66%，wall 降到 57%。

因此：不改默认调度，不启用浅层档或 gap 档，也不把 16→32 边际 gap 增益
直接做成延长到 64 的在线规则。若优化的是 `n≈100` 的总工作量，统一 64
目前更强；若优化的是“多数实例别回退”，统一 32 仍更稳。

## 新增观测

单实例可输出每次实际节点势上升的汇总：

```bash
./build/tsp_bb \
  --hk-node-ascent polyak \
  --hk-potential-update subtree-adaptive \
  --hk-update-depth 2 \
  --hk-update-iterations 16 \
  --hk-update-trace /tmp/node-ascent.csv \
  --hk-update-trace-max-depth 8 \
  data/classic/tsplib/st70.tsp
```

CSV 包括绝对深度、epoch 深度、层距、forced 边数、计划/实际评估数、初末
下界、初末相对 gap、是否改善/剪枝/安全早停，以及 gap/浅层分档标志。

其中：

```text
initial_relative_gap = (UB - initial_LB) / max(1, |UB|)
final_relative_gap   = (UB - best_LB) / max(1, |UB|)
gap_closed_ratio     = (best_LB - initial_LB) / (UB - initial_LB)
```

`--hk-update-trace-max-depth` 只过滤输出，不改变求解；本实验另设
`--hk-update-max-depth 8`，使势更新本身只发生在浅层。

## 当前早停路径

节点 Polyak/Helsgaun 上升在以下条件下提前结束：

1. 最强证书满足正式 `shouldPrune`，并用 `potential_updates_stopped_prunable`
   统计确实省下剩余轮数的尝试；
2. 次梯度范数为 0，即当前 1-tree 已满足所有度约束；
3. 当前下界在浮点容差内达到 incumbent；
4. 约束图不可行，或步长/势变为非有限值，或 Polyak 步长非正；
5. 显式启用 probe 后，早期 `gap_closed_ratio` 低于配置门槛。

第 1 项是不会改变搜索决策的安全早停。第 5 项是启发式筛选，会丢弃 probe
期间得到的临时势和证书。固定 patience 早停没有启用。

## 实验配置

- Release 构建，GAPMST 当前代码；
- `subtree-adaptive`、epoch 最小层距 2、Polyak；
- `--hk-update-max-depth 8`，更新尝试总预算不限；
- 默认 gap-change 门槛 `0.0001`，浅层保护到 depth 2；
- 每个配置、每个实例顺序运行一次；所有配置均返回已知最优值；
- wall time 是本机单次结果，仅用于本轮粗筛，节点数与迭代数是主要依据。

|:---|---:|---:|---:|---:|---:|

## 扩样：n≈96–124，以及 max-depth 8 的观测偏差

后续把观测窗口扩到 `gr96`、`rat99`、`eil101`、`lin105`、`pr124`、`rd100`、
`gr120`，并把 trace 升级为单次上升曲线：记录第 1/2/4/8/16/32/64 轮的
`gap_closed_ratio`，以及更新最终是 `rejected` / `pruned` / `installed`。
对 installed epoch 再记录后续子树 created/expanded、下界剪枝数和后代

## 当前早停机制（核对源码后）

节点 Polyak 上升在 `src/TspSolver.cpp` 的更新循环中提前结束，当且仅当：

1. 历史最强下界满足正式 `shouldPrune(best_LB, UB)`。整数成本使用
   `ceil(LB - tolerance) >= UB`。仅当确实省下至少一轮时计入
   `potential_updates_stopped_prunable`；
2. 次梯度范数为 0，即当前 1-tree 已满足全部度约束；
3. 当前下界在尺度化容差内达到 incumbent；
4. 约束图不可行，或 Polyak 步长非有限/非正，或势更新溢出；
5. 显式启用 probe 且早期 `gap_closed_ratio` 低于门槛。默认关闭。

连续 4 轮无改善只执行 `step_scale *= 0.5` 并清零计数器，**不会退出**。
固定 patience 早停此前已去掉，因为 8/12 轮后才改善的节点并不少。
所以当前没有“边际增益趋零即停”；核心是“已经能剪枝才停”。

## 如何度量一次更新该用多少轮

实例规模 `n` 和初始相对 gap **不能**单独决定轮数。`kroA100` 与 `kroE100`
都是 n=100，前者 64 轮把 created 从 9.6 万放到 18.0 万，后者从 50.0 万
收到 18.8 万。初始 gap 大只说明更不容易在中途 `shouldPrune`，不说明
前几轮有没有在涨。

可度量的单位是**这一次节点上升的覆盖率曲线**，trace 里已经有：

```text
coverage(k) = (LB_best(k) - LB_0) / (UB - LB_0)
T_first     = 第一次 coverage(k) > 0 的 milestone（1/2/4/8/16/32/64）
```

在 8 个分歧实例的全深度 64 轮 trace 上，installed epoch 的后续子树与
`T_first` 同向变化：

| T_first | installed 数 | 中位后续 created | 最大后续 created |
|---:|---:|---:|---:|
| 8 | 4,972 | 26 | 6,704 |
| 16 | 3,199 | 56 | 43,741 |
| 32 | 188 | 70 | 145,436 |
| 64 | 37 | 22 | 148,989 |

深度是先验，不是策略：

| 深度 | 中位 T_first | 16 轮仍零覆盖 | 中位后续 created |
|---:|---:|---:|---:|
| <=2 | 16 | 34.3% | 595 |
| 3--4 | 16 | 8.2% | 135 |
| 5--8 | 8 | 2.3% | 70 |
| >8 | 8 | ~3% | 22--38 |

因此实用量法是：

1. 用 `--hk-update-trace` 在统一 64 轮下采曲线，不要加 `--hk-update-max-depth`；
2. 对每次实际更新看 `depth`、`gap_closed_at_8/16/32/64`、`outcome`、
   `epoch_subtree_created`；
3. `T_first<=8`：多半 16--32 轮已够，再加容易改分支顺序；
4. `depth<=4` 且 `gap_closed_at_16≈0`：这是慢热浅层更新，只占 installed 的
   约 0.2%，却承载约 26% 的后续 created，是 32→64 真正该讨论的对象；
5. 若 32 轮仍几乎为零、64 轮才勉强动一点（如 `kroA100` depth=2、
   coverage(64)=0.003、后续 14.9 万），应视为噪声势，**不要安装**，而不是
   继续加预算。

现有安全早停已经自动完成另一半：小 gap、快接近剪枝线的节点会在 2--10 轮
停。剩下要调度的只是“还没剪枝、曲线还没启动”的浅层更新。按 `n`
或按初始 gap 给全局轮数，解决不了这个问题。

## 实验开关：浅层慢热延长

已实现、默认关闭：

```bash
./build/tsp_bb --hk-potential-update subtree-adaptive \
  --hk-update-depth 2 --hk-update-iterations 32 \
  --hk-update-slow-warm-depth 2 \
  --hk-update-slow-warm-iterations 64 input.tsp
```

规则：基础上限 32；仅不超过 `--hk-update-slow-warm-depth` 的更新允许把
上限抬到 64，并且必须第 16 轮仍无改善、到 32 轮已经抬升，才真正继续。
16 轮已有改善、或 32 轮仍无改善，都停在 32。第一轮 A/B 用 depth=4；
收紧后推荐 depth=2。

15 个 32/64 分歧实例、同一 Release 二进制、不限更新深度。CTest 8/8 通过。

## 超时实例与浅层分支顺序

1800s 超时的 7 个实例上，表里的最终下界等于根下界。这首先是口径
（未证完就回报根下界），也符合 DFS：第一支 `force` 的是已在 1-tree 上的边，
当前树不变，depth=1 下界等于根，另一侧 `forbid` 一直压在栈上。

只换 `--branch-edge-order weight|forbid-delta-desc|strong-top2` 不能抬
depth=1：对 1-tree 边 `force` 增益恒为 0。`--hk-update-depth 1` 能靠节点
势上升把 `si175` 的 depth=1 从 21343 抬到 21347，离最优 21407 仍远。

新增、默认关闭：

```bash
# 浅层先展开会改 1-tree 的 BP 孩子，再展开零增益 force 第一支
--bp-lift-first-depth 2

# 对根/浅层最好两条边先做有限轮势上升，再按 min(force,forbid) 选边
--branch-edge-order ascent-strong-top2
```

ascent strong 在根和绝对深度 1--2 生效，每侧最多 16 轮；force
试算使用与正式分支相同的 forced DSU、度满和子回路候选过滤。
试算次数和耗时分别记为 `branch_ascent_strong_probes` 与
`branch_ascent_strong_seconds`。

`si175` 上 `--bp-lift-first-depth 2` 后，第一个被展开的 depth=1 节点下界
变成 **21418.7**（超过最优 21407）。这是 forbid 前缀孩子；若 incumbent 已是
21407，该孩子应立即剪枝。零增益的 force 第一支仍在，只是被推迟。

再加 `--bp-split-zero-gain-depth 2`：force 一条已在 1-tree 中的边后若下界
不变，立刻对同一违规点上 forbid-delta 最大的另一条树边再切 force/forbid。
`st70` 仍得 675，并报告 22 次切分。`si175` 上 lift+split 的前几层下界为
21418 → 21428 → 21435，均高于最优；单独 split 时 force 侧第一层仍只抬
约 +2，真正大的抬升来自先走 forbid。因此推荐实验组合是两者一起开，默认
仍关闭。

## 后续建议

1. 不把 `--hk-update-max-depth` 当作加速手段；`--hk-update-trace-max-depth`
   只过滤日志。本轮 depth<=8 的搜索树比不限深度大 10–1000 倍。
2. 不启用浅层档或 gap 档默认值；也不加入短 patience 或“前 8 轮零覆盖就停”。
3. 当前 GAPMST 仍不改默认迭代上限。若启用 `--hk-update-slow-warm-*`，
   用 `--hk-update-slow-warm-depth 2` 而不是 4。
4. `kroD100`/`eil101` 的 64 轮收益来自 16 轮已经在涨的节点继续跑满，
   不要并进慢热规则。不要按 `n` 或初始 gap 给全局轮数。
5. 超时实例用 `--bp-lift-first-depth 2 --bp-split-zero-gain-depth 2`。
   `si175` 浅层下界已能超过最优；force 侧大子树是否因此剪得掉，要用
   LKH incumbent 做 300s/1800s 对照。不要先加势迭代。
6. 分层判据必须用整棵树的 created/expanded 和 wall time 验证。
